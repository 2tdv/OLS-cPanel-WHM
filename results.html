Test results: Apache against OpenLiteSpeed on cPanel

Before each release goes out, it runs for days on a real cPanel server under realistic traffic. These are the numbers of the test of October and November 2026 (a seven-day run from 30 October to 6 November and a two-day confirmation run from 9 to 11 November), measured, not estimated.

The test

  • One server: 2 CPU cores, 7.5 GB RAM, AlmaLinux 9, cPanel & WHM 11.138.
  • 25 hosting accounts with working sites: 12 WordPress (two WooCommerce shops, one with 600 posts, one in a subdirectory), 3 Joomla 6, 2 Drupal 11, 2 Laravel, 4 static sites, a PHP application with a long .htaccess and a site using server-side includes. Each CMS runs LiteSpeed's own cache plugin, and the WordPress sites use their account's object cache (Valkey, compatible with Redis), which OLS-cPanel-WHM sets up by itself.
  • Traffic that behaves like browsers: HTTP/2, compression, every image, stylesheet, script and font of each page, a browser cache, the shop's cart calls, logged-in editors and customers, search engine crawlers and a small share of attacks. About 350,000 page views and 2 million requests a day at the same daily curve, with peaks. A real browser on a second server visited the sites over the internet as well.
  • Changes all day long, as on a live server: account suspensions, PHP version switches, new domains and accounts, .htaccess edits, password changes and certificate renewals.
  • The planned steps worked: install, a reboot, a return to Apache, a second install, an update check and a complete uninstall that left nothing behind.

Results

Apache: a full day of cPanel's own Apache on this server (prefork, PHP-FPM; 31 October 2026). OpenLiteSpeed: a full day of OLS-cPanel-WHM 0.2.13 (10 November 2026). Both days carried the same traffic: 351,000 and 361,000 page views.

Response times are measured by the traffic generator on the server itself, per minute and per site, and summarised over the day. The CPU figures include the test's own traffic generator (about 5% of one core) on both days.

The object cache was running on both days: a return to Apache leaves it in place, so the WordPress sites under Apache used it too (13 instances, about 200 MB in both columns). The differences above therefore come from the web server, PHP and the page cache, not from the object cache. What did change: since release 0.2.13 the idle object cache instances use 0.8% of one core in total instead of 3.2%.

What makes the difference

  • Page cache. OpenLiteSpeed serves cached pages of WordPress, Joomla, Drupal and Laravel without running PHP.
  • A lighter PHP. LSAPI keeps each site's PHP ready with its compiled scripts and starts workers only when needed.
  • HTTP/2 and compression. One connection per visitor and compressed pages, where cPanel's Apache here used neither.
  • Browser caching. Images, stylesheets, scripts and fonts are kept by browsers for a week unless the site says otherwise, so return visits ask for less.
  • Attacks stopped early. ModSecurity with the OWASP rules runs inside OpenLiteSpeed, and probes for backups and secrets are refused before PHP.

What these numbers do not say

  • The sites are small and medium sites. A large shop with many logged-in customers, a heavy plugin or a large database changes the picture: pages for logged-in visitors are not cached.
  • One server, one week of traffic patterns. Your own results depend on your sites; the WHM plugin shows the cache hit rate and the load of each account so you can see them.
